# 本輪 C 盤清理工作評估（2026-11-23）

> 目的：把「掃描 → 分級 → 檢查 → 人工確認 → 刪除 → 複核」這條曾耗用大量對話輪次的流程，
> 固化成零 LLM 參與的 CLI 技能 `cdisk-guard`。本文件是設計依據，不是操作日誌。

## 一、總評

| 維度 | 本輪結果 | 評價 |
|---|---|---|
| 只讀掃描 | 完成，但 `scan_disk.ps1 -Deep` 跑 31 分鐘未收尾 | ❌ 效率與正確性皆有問題 |
| 安全分級 | A/B/C 三檔，C 檔鎖定 | ✅ 規則可用，應直接沿用 |
| 使用者維度 | 逐用戶／子目錄明細完整 | ✅ 但與主掃描口徑差 40 GB |
| 互動網頁 | 單檔、響應式、排序＋勾選＋全選 | ✅ 版式可復用 |
| 刪除能力 | 靜態頁只产出 JSON 清單，不能真刪 | ❌ 必須補本機後端 |
| 刪除執行 | 淨釋放 3.41 GB（預估 16.9 GB） | 🟡 成功但可歸因性不足 |
| 授權流程 | 兩次人工確認，符合安全規則 | ✅ 但每次都靠 LLM 對話，成本高 |
| Token 消耗 | 數十輪工具呼叫處理機械性工作 | ❌ 最大改進空間 |

**核心結論**：這輪工作的判斷（分級、安全邊界）值得保留，但「執行」不該由 LLM 逐次驅動。
判斷固化成規則表，執行固化成 Python 程式，LLM 只在「建立技能」時進場一次，之後運行期消耗 **0 積分**。

## 二、逐項技術債與對應改進

### 1. Junction／Reparse Point 導致重複計算
- 現象：主掃描 `C:\Users` = 178.40 GB，逐用戶統計 = 137.83 GB，差約 40 GB。
- 根因：`Get-ChildItem -Recurse` 會跟隨 `AppData\Local\Application Data` 等自引用 junction。
- 改進：`cdiskctl.py scan` 用 `os.scandir` 迭代堆疊遍歷，`follow_symlinks=False`，
  並檢查 `st_file_attributes & 0x400`（FILE_ATTRIBUTE_REPARSE_POINT）直接跳過。
  **單次遍歷、單一資料來源**，不再有兩套口徑。

### 2. 深層掃描逾時
- 現象：技能內建 `-Deep` 在使用者目錄反覆計算，31 分鐘後手動終止。
- 改進：一次遍歷同時聚合六個維度（根目錄／各用戶／用戶子目錄／垃圾點／AppData／大檔），
  並加 `scan_budget_sec` 時間上限（預設 600 秒），超時即輸出已收集結果，不無限等待。

### 3. 父子目錄重複計入選取統計
- 現象：A 檔 27 項中，`Temp` 下的 10 個子項已包含在 `Temp` 的 5,179.5 MB 內，
  帳面 24.51 GB 實際約 22.92 GB。
- 改進：`scan` 階段即計算 `nested_in`，`delete` 階段自動剔除子項；
  網頁統計同步顯示「帳面／實際」兩個數字。

### 4. 瀏覽器沙箱無法刪檔
- 現象：`file://` 靜態頁只能下載 `cdisk-delete-plan.json`，需回到 WorkBuddy 由我逐項執行。
- 改進：`serve` 啟動只綁 `127.0.0.1` 的 Python stdlib HTTP 後端（隨機埠＋一次性 token），
  網頁「執行刪除」直接 `POST /api/delete` 觸發本地刪除流程。這正是本輪留下的待辦，本技能予以補齊。

### 5. 回收站 API 對系統／佔用中目錄失敗
- 現象：第一批 10 項中 7 項回報「系統呼叫層級不正確／此系統不支援」，
  `Test-Path` 確認目標仍在，非誤報；需向使用者取得第二次授權才降級為直接刪除。
- 改進：不再浪費一次失敗嘗試。規則表直接標記 `delete_method`：
  一般快取 → `direct`（本次已授權之流程）；`$Recycle.Bin` → `SHEmptyRecycleBinW`；
  `Explorer` → 只刪 `thumbcache_*.db`。降級與其例外在設定檔中預先聲明，由使用者在安裝時一次授權。

### 6. `SAFE_DELETE_BULK_CONFIRM_REQUIRED` 造成部分刪除
- 現象：`Remove-Item -Recurse` 觸發 WorkBuddy 工具層的大量刪除確認鉤子（>50 檔／目錄），
  依技能規則未對同一目標重試，導致 Temp 9,999→1,141、Chrome／Edge Cache 各→2 等殘留。
- 關鍵認知：**這是 WorkBuddy 工具呼叫層的鉤子，不是 Windows 限制**。
  獨立 Python 行程（由工作排程啟動）不受此鉤子約束。
- 改進：改用 Python `shutil.rmtree`／逐檔 `os.unlink`，逐項容錯（鎖定檔略過並記數），
  不會因單一目錄檔案過多而整批中止。

### 7. `Clear-RecycleBin` 只作用於目前 SID
- 現象：回報 OK，但 4,564.9 MB／7,150 檔全在另一使用者 SID `…‑1001` 的回收站，
  目前執行身分為 SID `…‑500`，清不掉。涉及他人資料，當時未擅自處理。
- 改進：改用 `shell32.SHEmptyRecycleBinW(NULL, NULL, …)` 清理所有磁碟；
  執行後仍逐 SID 掃描 `$Recycle.Bin` 回報殘留，殘留一律列入「需人工處理」，絕不靜默略過。

### 8. 空間量測受外部寫入干擾
- 現象：剩餘空間 15 GB → 9.4 GB → 7.5 GB 持續下降，最後觀測淨增 3.41 GB 無法精確歸因。
- 改進：刪除前後都用同一個 `GetDiskFreeSpaceExW` 取值，並記錄「觀測淨值」與
  「目標帳面值」兩個數字，明確標註差值可能來自其他程式寫入，不冒充精確成果。

### 9. 備份受限於單碟
- 現象：只有 C:、執行前剩 9.4 GB，全量位元備份會先耗盡空間，只能備份 52 MB 小項。
- 改進：規則化為「<100 MB 項目做 ZIP 實體備份 ＋ 全部項目寫完整 manifest」，
  並在網頁與紀錄中明確標示可還原範圍，不再每次臨場判斷。

## 三、確認流程的取捨

本輪做了兩次人工確認（「確認執行A」、降級直接刪除授權），這是必要且正確的，不應簡化掉。
改進方向不是取消確認，而是**把確認點從 LLM 對話移到固定介面**：

| 確認點 | 本輪 | 技能化後 |
|---|---|---|
| 選擇要刪什麼 | 對話貼清單 | 網頁 checkbox（預設勾選 A 檔） |
| 危險警示 | 對話加粗文字 | 刪除前 modal，逐項列出完整路徑（不變） |
| 不可逆授權 | 對話問答 | 安裝時一次授權 ＋ modal 內「我已瞭解，執行」 |
| 結果複核 | 我逐項 Test-Path | 程式逐項 `os.path.exists` ＋ 寫入執行紀錄 |

## 四、積分消耗估算

| 項目 | 本輪 | 技能化後 |
|---|---|---|
| 建立／改進規則 | 數十輪 LLM 對話 | 一次性（本次） |
| 每次磁碟分析 | LLM 驅動多支 PowerShell | `python scan`，0 LLM |
| 每週一例行檢查 | 若用 WorkBuddy 自動化，每次喚醒 LLM | OS 工作排程跑 `watch`，0 LLM |
| 門檻警示 | 需對話 | 原生 Win32 視窗，0 LLM |
| 刪除執行與複核 | 十餘次工具呼叫 | 單一行程內完成，0 LLM |

**結論**：不要用 WorkBuddy 的排程自動化來做這件事——它每次觸發都會喚醒模型、消耗積分。
正確做法是 OS 層級的工作排程（登入時啟動 `pythonw.exe cdiskctl.py watch`），
WorkBuddy 只在需要改規則或看報告時才被叫醒。

## 五、沿用與捨棄

- ✅ 沿用：A/B/C 規則表、`C_ROOT`／`C_USERITEM`／`A_JUNK` 黑名單、深色單檔網頁版式、
  六個區塊、即時統計、完整路徑去重、小項備份、manifest、逐項複核、執行紀錄格式。
- ✅ 沿用：`npm-cache` 預設排除（本輪使用者明確指示）、`nested_in` 標記、C 檔永不進入清單。
- ❌ 捨棄：`scan_disk.ps1 -Deep`、`Add-Type`／COM 路徑、`-Recurse` 遍歷、
  `Clear-RecycleBin -DriveLetter`、靜態頁下載 JSON 的間接刪除。
- ➕ 新增：ctypes 原生雙按鈕警示框、127.0.0.1 後端、週一低 CPU 排程、2% 門檻、狀態去重。
